# Connect Capital

Trusted transaction infrastructure for small-business financing. MCA is the
initial wedge.

**Status: M0–M11 complete. 273 tests passing. Not yet wired to live
infrastructure.**

- M0 kernel — identity, permissions, audit
- M1 merchant intake — prequal, application, documents, uploads
- M2 provider — verification, criteria, appetite, decline taxonomy
- M3 matching — grading, blinded cards, match runs, authorization
- M4 provider workspace — blinded queue, view resolution, document requests
- M5 banking — metrics, position detection, renewal timing, re-eligibility
- M6 messaging — scoped threads, contact-detail flagging, notification escalation
- M7 underwriting — state machine, structured declines, merchant aggregation
- M8 offers — disclosure engine, estimated APR, revisions, negotiation
  **(disclosure method requires counsel sign-off before launch)**
- M9 funding — confirmation, fee accrual, transaction timeline
- M10 admin — hypothesis scorecard, trust and safety detection
- M11 hardening — preflight verification, threat model, elevation, legal hold

### Setup

```bash
npm install
cp .env.example .env.local        # fill in credentials
npm run db:push                   # apply Drizzle schema
psql $DATABASE_URL -f migrations/0001_kernel_guards.sql
psql $DATABASE_URL -f migrations/0002_merchant_intake.sql
psql $DATABASE_URL -f migrations/0003_provider_verification.sql
psql $DATABASE_URL -f migrations/0004_matching_authorization.sql
psql $DATABASE_URL -f migrations/0005_banking.sql
psql $DATABASE_URL -f migrations/0006_messaging_underwriting.sql
psql $DATABASE_URL -f migrations/0007_offers.sql
psql $DATABASE_URL -f migrations/0008_funding_fees.sql
psql $DATABASE_URL -f migrations/0009_admin_security.sql
npm run db:seed                   # TEST-labelled fixtures only
npm test
npm run preflight                 # verifies the guards are ACTUALLY applied
```

`npm run preflight` is the gate before any deploy. Every guarantee in this
system has a TypeScript half that fails loudly and a database half that fails
**silently** — a skipped migration leaves an application that behaves perfectly
and an audit log anyone can edit. Preflight checks the database half.

Read `SECURITY.md` before touching anything in `lib/`.

Migrations 0001–0009 are **not** optional and **not** generated by Drizzle.
They contain the append-only grants, the audit hash chain, and the RLS
policies. Schema without them is a database where the audit log can be edited.

### Non-negotiables

These are load-bearing. Changing any of them silently breaks a promise the
company makes to merchants:

- **Never read the acting org from a request.** It comes from the session, via
  `resolveActor`. Accepting an `orgId` parameter is the canonical multi-tenant
  breach and it does not look like one in review.
- **Never serve documents from a signed URL.** All reads go through
  `deliverDocument`, which logs before it streams. The access log is the
  product.
- **Never write outside `mutate()`.** It couples the audit row to the domain
  change in one transaction. An audit row that can commit separately from its
  cause is not evidence.
- **Never add a table without classifying it.** State, or evidence? Evidence
  gets `REVOKE UPDATE, DELETE` in the same migration that creates it.
- **Never seed a verified provider.** The badge means a real KYB check ran.
- **Never build a blinded card by deleting fields.** `lib/blinded.ts` constructs
  from an allowlist so a newly added merchant field cannot leak by default. A
  denylist fails open; that is the whole difference.
- **Never let anything but a merchant grant an authorization.** Enforced in
  `policy.ts` and again by trigger in 0004.
- **Never expose raw bank transactions to a provider.** They carry the
  merchant's entire customer and vendor list. Funders see `financial_profiles`;
  no authorization scope reaches the transaction table.
- **Never count an MCA advance as revenue.** `isRevenueDeposit` handles it and
  the tests pin it. Getting this wrong inflates a merchant's numbers exactly
  when they are most leveraged.
- **Never price a funding at today's rate.** Fees resolve against the schedule
  in effect on the FUNDING date. Re-running a report must not reprice deals
  that already went out on an invoice.
- **Never render an audit event to a merchant that isn't in `RENDERERS`.**
  `lib/timeline.ts` is an allowlist. The audit log carries refused access
  attempts and admin elevation reasons.
- **Never ship the disclosure engine to a regime state without counsel sign-off.**
  `lib/disclosure.ts` computes correct arithmetic under one explicit method. It
  is not validated compliance, and the state-specific method varies.
- **Never recompute a stored disclosure on read.** It is frozen with its
  ruleset version and hash. The question is always "what was the merchant shown
  and when", never "what would we show now".
- **Never forward an underwriter's internal note to a merchant.** It is written
  for their own team. `perProviderLabel` decides what the merchant sees.
- **Never stream raw declines to a merchant.** `aggregateDeclines` exists so
  five funders citing one reason reads as one fact with a remedy, not five
  rejections.
- **Never add a second way to load a merchant file.** `resolveProviderView` is
  the only path, and it returns identity only against a live grant. A separate
  "full file" loader makes blinding depend on a developer's routing choice
  rather than on whether the merchant said yes.

### Deliberate omissions

- **No money movement.** The funder wires the merchant directly; the platform
  records the event and invoices its fee. This avoids money transmitter
  licensing in ~50 jurisdictions and is a product decision, not an oversight.
- **No automated credit decisioning.** Out of scope by design.
- **No e-signature.** Funding documents are the funder's paper.
